# Intent to Done

사용자가 원하는 결과를 충분히 인터뷰하고, 확정한 계약을 테스트와 실제 동작으로 확인한다. 보고에는 [쉬운 설명 규칙](references/reporting.md)을 적용한다. 이 스킬은 자동 선택될 수 있지만, 작업의 승인과 실행 권한을 새로 부여하지 않는다.

## 시작과 작업 범위

- 현재 요청, 프로젝트 지침, 관련 문서와 실제 Git 상태를 필요한 범위에서 읽는다. 사용자 변경과 기존 승인, 보류 사항을 보존한다.
- 새 프로젝트는 전체 목표와 주요 경계를 먼저 합의하고 작동하는 기능 단위로 반복한다. 기존 프로젝트는 구조와 실행 기준선을 확인한다. 재개는 [작업 상태](references/work-state.md)를 복원한다.
- 작업 크기는 파일 수만으로 판단하지 않고 영향, 불확실성, 되돌리기 어려움을 함께 본다. 작은 작업은 대화와 기존 문서의 짧은 항목으로 충분하다.
- 조사나 설명만 요청하면 변경 없이 [how](playbooks/how.md), [why](playbooks/why.md), [teach](playbooks/teach.md) 중 필요한 기능만 사용한다. 세 기능은 구분하되 기본은 모두 주 담당이 실행하며, 기능별 보조나 병렬 조사자를 자동 호출하지 않는다.

## 진행 모드와 사용자 결정

기본은 단계별 확인이다. 각 단계의 결과물과 필요한 근거를 보여주고 다음 단계 진행을 기다린다. 동의의 대상은 직전 제시한 산출물과 범위이며, 이미 받은 동의를 반복해서 받지 않는다. 무응답을 동의로 처리하지 않는다.

사용자가 특정 구간을 자동 진행하라고 명령하면 그 범위를 기록하고 구간 내 사용자 대기를 생략한다. 새로운 목표나 기대 동작의 선택까지 위임했다고 해석하지 않는다. 결정권까지 명시적으로 위임한 경우 그 범위와 한계를 따른다. 위임 밖의 중요한 미결은 질문하고, 답에 의존하지 않는 조사는 계속할 수 있다.

추천, 조사한 사실, 사용자 확정, 미결과 보류를 구분한다. 의도와 SDD에서는 근거 없는 기본값을 채워 확정하지 않는다.

## 단계와 필요한 플레이북

해당 단계의 플레이북만 읽는다. 모든 참조를 시작부터 한꺼번에 로드하지 않는다.

| 단계 | 수행할 내용과 다음 단계 조건 |
| --- | --- |
| 0. 현황 | 관련 지침, 코드, 실행 방법, 기존 실패와 작업 상태 확인. 조사만 요청했으면 해당 기능으로 종료. |
| 1. 의도 | [의도 인터뷰](playbooks/intent-interview.md). 목표와 범위, 제약과 성공 판정의 충분한 인터뷰, 사용자 확정. |
| 2. SDD와 계획 | [사양 인터뷰](playbooks/spec-plan-interview.md). 동작, 예외, 유지할 계약, 인수 조건, 구현 방향과 순서 확정. |
| 3. 테스트 | [테스트](playbooks/testing.md). 쉬운 시나리오와 실제 변경 전 실행 근거를 함께 보고하고 확인받음. 새 동작과 버그는 RED, 동작 보존 리팩터링은 통과 기준선. |
| 4. 구현 | [구현](playbooks/implementation.md). 작은 단위로 구현과 자체 검증 후 결과물을 보고하고 독립 검증 진행을 확인받음. |
| 5. 독립 검증 | [검증](playbooks/verification.md). 별도 컨텍스트의 검증 결과를 보고하고 사용자 판단. |
| 6. 마감 | 실제 변경과 검증, 미확인과 남은 일을 짧게 보고하고 기존 정본과 상태를 갱신. 구현, 검증, 배포 완료를 구분. |

자동 진행 구간에도 테스트와 독립 검증 조건은 유지한다. 실패와 미실행을 통과로 기록하지 않는다. 실행할 수 없는 필수 검증이 있으면 구현 상태와 이유를 보고하고 검증 완료를 보류한다.

## 확정한 테스트와 수정 규칙

- 자동 TDD 예외는 동작 변경 없는 문서, 주석, 포맷팅과 폐기용 목업, 프로토타입이다. 이유와 대체 검증을 보고한다. 실제 기능 편입 시 정상 개발 절차로 돌아간다. 스타일, 설정, 생성 코드라는 이유만으로 목록을 확대하지 않는다.
- 최초 테스트 단계에서 시나리오와 실제 근거를 함께 확인받는다. 이후 진행을 허용한 구현 단위에서는 확정 사양 안의 추가 테스트를 자동 작성하고 실행한다. 새로운 기대 동작, 사양이나 별도 기능 범위가 생기면 사용자 확인으로 돌아간다. 다음 단계까지 자동 승인된 것으로 보지 않는다.
- 같은 근본 문제에 대한 자동 수정과 재검증은 최대 두 차례다. 최초 발견과 예상한 TDD의 RED는 횟수에 넣지 않는다. 문제나 테스트 이름을 바꾸거나 세션을 재개해 횟수를 초기화하지 않는다.
- 두 차례 후에도 실패하면 자동 수정을 멈추고 원인, 시도와 근거, 다음 선택지를 보고한다. 근거 없는 수정을 상한까지 반복할 필요는 없다.
- 변경 전부터 있었고 이번 변경과 무관하다는 근거가 있는 실패는 구분해 보고하며 진행한다. 전체 검사 통과로 표시하지 않으며, 프로젝트의 필수 통과 조건을 우회하지 않는다.

## 에이전트와 모델

주 담당 포함 동시 최대 3개, 보조 최대 2개다. 단계별 에이전트를 항상 만들지 않는다. how, why, teach의 기본 실행은 주 담당이다. 독립 검증은 [검증 플레이북](playbooks/verification.md)에 따라 별도 컨텍스트의 담당자 한 명으로 시작한다.

위임 시 원래 목표, 확정 계약, 소유 경로, 금지 범위, 검증 기준과 대상 코드 상태를 전달한다. 같은 파일과 공통 상태, API 계약의 동시 변경은 소유자를 정하거나 순서를 정한다. 보조의 재위임도 전체 상한에 포함하며 주 담당이 허용하지 않은 추가 호출은 하지 않는다. 별도 worktree는 사용자나 프로젝트가 허용할 때만 사용한다.

현재 도구에서 확인된 설정만 사용한다. 미설정 역할은 부모 모델과 추론을 상속하며, 이는 저비용 모델 자동 선택을 뜻하지 않는다. 모델 설정을 바꾸는 작업은 intent-to-done-setup 스킬이 맡는다. 이 스킬을 실행했다는 이유로 전역 설정을 변경하거나 추가 API 과금과 크레딧 사용으로 전환하지 않는다.

도구별 호출과 한계는 실제 환경이 [Codex](references/codex.md)일 때 또는 [Claude Code](references/claude-code.md)일 때만 해당 문서를 읽는다. 요청 설정과 확인 가능한 적용값을 구분하며, 확인할 수 없으면 그대로 보고한다.

## 정본과 근거

대화에만 남기면 재개가 어려운 작업은 기존 작업 문서 한 곳에 [상태 항목](references/work-state.md)을 둔다. 사양의 인수 조건, 테스트, 실제 결과를 같은 식별자로 연결할 수 있지만 별도 장부를 강제하지 않는다. 변경된 계약은 코드와 같은 변경 묶음에서 정본에 반영한다. 커밋, PR, 병합, 배포는 사용자가 맡긴 범위와 프로젝트 운영 규칙을 따른다.

이 패키지는 지침이다. 자동 선택과 절차 준수를 보장하는 실행 엔진이 아니다. 프로젝트에 필요한 강제 검사는 지원되는 테스트와 CI 등으로 뒷받침하며, 없는 훅이나 기능을 있다고 설명하지 않는다. 출처와 조정 내역은 [자료](references/sources.md)를 필요할 때 확인한다.
