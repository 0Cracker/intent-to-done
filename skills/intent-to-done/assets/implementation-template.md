# 구현 계획과 실행 기록

- 저장 파일: implementation.md, 기존 구현 기록이 있으면 해당 위치 유지
- 작업 기록, 의도와 사양: 생성 후 실제 상대 링크로 연결
- 기준 사양 버전과 승인 근거 위치:
- 현재 상태: 계획 초안, 구현 미착수
- 대상 코드 상태와 실행 환경:

계획과 실행을 구분하고 미실행 테스트와 변경은 예정으로 표시한다. 무관한 항목은 생략하며 승인 상태와 누적 수정 횟수는 task.md를 정본으로 삼는다.

## 계획, 작업 단위와 소유권

| 작업 단위 ID | 관련 인수 조건 | 변경할 파일과 내용 | 소유자와 공유 계약 | 선행 작업 | 완료 검사와 기대 결과 |
| --- | --- | --- | --- | --- | --- |

- 가장 위험한 단계와 깨질 수 있는 기존 동작:
- 변경 금지 경로, 데이터와 유지할 계약:
- 확인할 가설과 되돌릴 방법:
- 테스트 도구와 최소 골격을 준비할 범위:
- 담당자 재량과 다시 확인할 결정:

파일이 달라도 같은 상태나 API를 바꾸면 소유자와 순서를 조정한다. 초기 계획은 사양과 함께 검토하도록 저장한다. 구현 착수와 자동 진행은 task.md의 사용자 지시 범위를 따른다.

## 실행 이력

실행마다 RUN-001 같은 ID로 기록을 추가하고 이전 기록은 보존한다. 수동 검사는 실제 조작과 관찰을 적고 종료 코드를 지어내지 않는다.

- 실행 ID와 구분: RED, GREEN, 기준선, 회귀 또는 독립 검증
- 관련 사양 버전, 인수 조건 ID, 작업 단위와 테스트 케이스:
- 실제 실행 시각, 명령 또는 수동 조작, 작업 위치:
- 대상 코드 상태: branch와 HEAD, 관련 미커밋과 미추적 파일의 식별, Git이 없으면 파일과 해시
- 관련 환경과 입력, 관찰할 경계:
- 요구에서 구한 기대 결과와 근거:
- 실제 관찰과 종료 코드, 미실행이면 이유:
- RED라면 의도한 실패인지, 환경 문제와의 구분:
- 로그와 캡처의 상대 링크, 판정과 제한:

짧은 결과는 직접 기록한다. 긴 근거는 evidence/ 또는 기존 보관 경로에 실행별 고유 이름으로 저장한다. RED와 GREEN을 덮어쓰지 않는다.

### 결함 수정 시도

| 문제 ID와 시도 번호 | 원인과 바꾼 내용 | 재검증 실행 ID와 실제 결과 | 후속 행동 |

상한에 포함되는 수정은 task.md의 문제 ID와 누적 횟수에 연결한다. 예상한 RED를 해결하는 최초 구현은 추가 수정으로 세지 않는다.
