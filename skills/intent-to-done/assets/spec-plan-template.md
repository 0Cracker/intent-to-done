# SDD, 요구사항과 설계

- 저장 파일: SDD.md, 기존 사양 정본이 있으면 해당 위치 유지
- 작업 기록과 확정 의도 위치: 생성 후 task.md, intent.md와 실제 상대 링크로 연결
- 현재 사양 버전과 상태: 미작성, 미승인
- 관련 코드, 문서와 관측 근거:

## 의도에서 이어받은 결정

- 해결할 문제와 관찰 가능한 결과:
- 범위, 비목표와 기존 구조의 변경 허용 경계:
- 성공 판정 방식과 순서:

| 질문 ID | 답변 또는 조사 결과와 근거 | 사양 반영 위치 | 남은 미결, 사용자 보류와 재개 조건 |
| --- | --- | --- | --- |

의도의 질문마다 처리 위치를 남긴다. 구현에 필요한 미결은 해결하거나 사용자 승인으로 범위를 좁힌다.

## 현재 동작과 선택한 방향

- 관측한 현재 흐름과 결함, 아직 존재하지 않는 부분:
- 선택한 방향과 근거:
- 중요한 다른 대안과 채택하지 않은 이유:
- 관련 프로젝트 규칙, 충돌과 해결해야 할 우려:

새 프로젝트의 현재 동작과 코드 위치를 지어내지 않는다. 의미 있는 선택이 없으면 대안을 억지로 만들지 않는다.

## 동작 계약

| 흐름 | 시작 조건과 입력 | 처리 경계와 상태 소유자 | 관찰 가능한 결과와 종료 상태 | 실패와 재시도 시의 약속 |
| --- | --- | --- | --- | --- |

- 유지할 공개 인터페이스와 데이터 의미:
- 이번 변경에 실제로 관련 있는 보존, 접근, 중복 처리와 호환성 조건:
- 성능이나 수치 조건이 있다면 값의 근거, 비교 조건과 허용 범위:

관련 없는 정책과 수치 목표는 추가하지 않는다. 근거가 없는 값은 제안 또는 미결로 둔다.

## 인수 조건과 증명

| 인수 조건 ID | 정상, 경계 또는 회귀 시나리오와 입력 | 관찰 가능한 기대 결과 | 정답의 독립된 근거 | 검사 수단과 테스트 위치 | 관련 질문 ID |
| --- | --- | --- | --- | --- | --- |

- 신규 동작과 버그의 실제 RED를 확인할 방법, 리팩터링이면 변경 전 기준선:
- 필요한 최소 실행 환경과 준비 범위:
- 실제 사용자 경계를 확인할 방법과 실행이 어려운 검사:

검사 방법은 계획이며 실행 결과는 implementation.md 실행 이력에 따로 남긴다. 단위 검사로 확인하지 못한 연결과 실제 조작은 통과로 간주하지 않는다.

## 구현 계획과의 경계

- 구현 계획의 위치: implementation.md, 생성 후 실제 상대 링크로 연결
- 설계상 중요한 위험과 유지할 경계:
- 구현 담당이 재량으로 정할 수 있는 것과 재확인이 필요한 것:

구현 순서, 변경 파일과 소유권은 implementation.md에서 관리한다. SDD.md는 요구와 설계 계약을 유지하며 실행 결과를 계획과 섞지 않는다.

## 단계 진입과 변경 처리

- 이번에 요청할 승인 대상: 사양 버전, 구현 방향과 단계 범위
- 기존 승인으로 유지되는 부분과 추가 확인이 필요한 부분:
- 코드와 사양이 달라질 때 갱신할 정본 위치:
- 다음 담당자가 처음 읽고 실행할 지점:

승인과 변경 이력은 작업 기록에서 관리한다. 사양 확정을 다음 단계의 실행 권한으로 확대하지 않는다.
