# 구현과 자체 검증

진행을 허용한 기능 단위에서 확정 계약을 구현한다. 테스트 단계 확인 없이 실제 기능 로직을 먼저 작성하지 않는다. 자동 진행 구간이어도 시작 근거는 필요하다.

## 작업 방식

- 입력부터 실제 호출자와 상태 소유자, 소비자까지 확인한 뒤 변경한다. 기존 코드와 표준 기능, 설치된 의존성을 우선 사용한다.
- 기존 코딩 지침을 적용하되, 단순화 때문에 요청한 동작과 입력 경계 검증, 데이터 보호, 접근성, TDD와 검증을 제거하지 않는다.
- 계약을 만족하는 최소 변경을 만들고 작은 완결 단위로 확인한다. speculative fallback과 retry를 덧붙이기 전에 원인 가설을 실행으로 확인한다.
- 신규 기능은 관찰 가능한 결과 하나씩, 버그는 실제 재현과 원인, 리팩터링은 기존 동작의 보존을 중심으로 진행한다.
- 성능 개선은 비교 조건과 기준선을 먼저 확보하고, 같은 조건의 수정 후 측정과 기능 회귀를 확인한다.

확정 사양 안의 추가 테스트와 작은 수정은 자동 수행하고 결과에 포함한다. 새로운 기대 동작이나 범위를 발견하면 임의로 채우지 않고 사양 인터뷰로 돌아간다. 범위 밖 발견은 후보로 보고하며 자동으로 수정하지 않는다.

## 병렬 작업과 검증 대상

필요한 경우에만 보조를 사용한다. 주 담당 포함 총 3개 상한을 지키고 소유 경로와 공유 계약의 담당을 정한다. 여러 에이전트가 같은 파일이나 공유 상태를 동시에 수정하지 않도록 순서를 조정한다. 테스트와 fixture의 소유권도 포함한다.

검증 대상으로 넘길 코드 상태를 고정하고, 검증 중 같은 대상을 수정하지 않는다. 불가피하게 바뀌면 검증자에게 알리고 결과를 새 상태에 맞춰 갱신한다. 다른 작업자의 변경을 자신의 실험 정리 과정에서 지우지 않는다.

## 검증과 자동 수정 상한

관련 검사부터 시작하고 기능 단위가 완성되면 영향받는 회귀, 프로젝트 필수 검사와 실제 대상의 동작을 확인한다. 성공 근거가 있는 같은 검사를 이유 없이 반복하지 않는다. 독립 검증자는 필요한 검사를 직접 확인할 수 있다.

예상한 RED를 해결하는 최초 구현 이후 결함을 발견하면 같은 근본 문제에 수정과 재검증을 최대 두 차례 수행한다. 두 차례 후에도 실패하면 멈춰 원인 가설, 바꾼 내용과 실행 결과, 다음 선택지를 보고한다. 실패 테스트가 여러 개라도 같은 원인이면 같은 문제로 센다. 명칭이나 담당, 세션을 바꾸어 횟수를 초기화하지 않는다.

사양 변경이 필요하면 횟수와 무관하게 먼저 확인한다. 환경과 사용량 때문에 실행하지 못하면 미실행으로 남긴다. 기존 실패는 변경 전후 상태와 관련 경로 근거로 이번 변경과의 관계를 판단하고 불확실하면 미확인으로 보고한다.

## 사용자에게 보여줄 결과

실제 바뀐 동작이나 화면, 자체 검증 결과와 근거, 미확인과 남은 실패, 사양과의 차이를 보고한다. 기본 모드에서는 독립 검증으로 넘어갈지 확인받는다. 자동 진행 명령이 그 구간을 포함하면 근거를 남기고 진행한다.
