# 구현과 자체 검증

허용된 기능 단위의 확정 계약을 구현한다. 테스트 단계 확인 전 기능 로직을 작성하지 않는다. 자동 진행에도 시작 근거는 필요하다.

## 작업 방식

- 입력, 실제 호출자, 상태 소유자와 소비자를 확인한 뒤 변경한다. 기존 코드, 표준 기능과 설치된 의존성을 우선 쓴다.
- 기존 코딩 지침을 따른다. 단순화를 위해 요청 동작, 입력 경계 검증, 데이터 보호, 접근성, TDD와 검증을 제거하지 않는다.
- 계약을 만족하는 최소 변경을 작은 완결 단위로 확인한다. speculative fallback과 retry 추가 전 원인 가설을 실행으로 확인한다.
- 신규 기능은 관찰 가능한 결과 하나씩, 버그는 실제 재현과 원인, 리팩터링은 기존 동작 보존을 중심으로 진행한다.
- 성능 개선은 비교 조건과 기준선을 먼저 확보한다. 수정 후 같은 조건으로 측정하고 기능 회귀를 확인한다.

확정 사양 안의 추가 테스트와 작은 수정은 자동 수행하고 보고한다. 새 기대 동작이나 범위는 임의로 채우지 않고 사양 인터뷰로 돌아간다. 범위 밖 발견은 후보로만 보고하고 자동 수정하지 않는다.

## 병렬 작업과 검증 대상

필요할 때만 보조를 쓴다. 주 담당 포함 총 3개 상한을 지키고, 테스트와 fixture까지 소유 경로와 공유 계약의 담당을 정한다. 같은 파일과 공유 상태를 동시에 수정하지 않도록 순서를 조정한다.

검증 대상 코드 상태를 고정하고 검증 중 수정하지 않는다. 불가피하게 바뀌면 검증자에게 알리고 결과를 갱신한다. 실험 정리 중 다른 작업자의 변경을 지우지 않는다.

## 검증과 자동 수정 상한

관련 검사부터 시작한다. 기능 단위가 완성되면 영향받는 회귀, 프로젝트 필수 검사와 실제 대상 동작을 확인한다. 통과 근거가 있는 검사를 이유 없이 반복하지 않는다. 독립 검증자는 필요한 검사를 직접 확인할 수 있다.

예상한 RED를 해결한 최초 구현 이후 결함은 같은 근본 문제별로 최대 두 차례 수정하고 재검증한다. 두 차례 후에도 실패하면 멈추고 원인 가설, 변경 내용, 실행 결과와 다음 선택지를 보고한다. 실패 테스트가 여러 개라도 같은 원인이면 한 문제로 센다. 명칭, 담당과 세션 변경으로 횟수를 초기화하지 않는다.

사양 변경은 횟수와 무관하게 먼저 확인받는다. 환경과 사용량 때문에 실행하지 못하면 미실행으로 남긴다. 기존 실패와 이번 변경의 관계는 변경 전후 상태와 관련 경로로 판단하고, 불확실하면 미확인으로 보고한다.

## 사용자에게 보여줄 결과

바뀐 동작이나 화면, 자체 검증 결과와 근거, 미확인, 남은 실패와 사양 차이를 보고한다. 기본 모드에서는 독립 검증 진행을 확인받는다. 자동 진행 범위에 포함되면 근거를 남기고 진행한다.

문서 모드에서는 [구현 템플릿](../assets/implementation-template.md)을 바탕으로 `implementation.md`의 기존 계획에 실제 변경, 자체 검증, 실행별 근거와 결함 수정 시도를 누적한다. 문제별 누적 횟수는 `task.md`에서 관리하고 시도별 기록을 연결한다.

독립 검증 승인 요청과 인계 전 대상 코드 상태, 사양 버전과 실행 근거 링크를 저장한다. `task.md`의 현재 단계와 다음 행동도 갱신한다. 기존 통합 기록은 [작업 상태 지침](../references/work-state.md)에 따라 해당 위치를 유지한다.

사양 차이에는 이유, 영향받는 인수 조건, 재확인 범위와 정본 반영 위치를 기록한다. 사용 중인 인계 문서의 사양 버전과 코드 상태도 맞춘다. 검증 인계는 검증 플레이북의 전달 항목을 쓰고, 구현 인계 문서를 새로 만들지 않는다.
