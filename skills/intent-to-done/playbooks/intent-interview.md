# 의도 인터뷰

문제, 원하는 결과와 하지 않을 일을 사용자가 판단할 수 있는 짧은 의도를 만든다.

1. 사용자 말과 기존 확정 사항으로 초안을 쓴다. 문제, 영향받는 사람과 상황, 원하는 결과, 범위, 제약, 비목표와 성공 판정 근거를 적는다.
2. 빈칸과 모호한 표현을 한 번에 1~3개씩 묻는다. 남은 질문은 여러 차례 이어가되, 질문 수를 채우려고 이미 답한 것을 반복하지 않는다.
3. 현재의 구체적 사례, 원하지 않는 결과와 반대 사례를 요청한다. “좋게”, “빠르게”, “예쁘게”의 뜻을 사용자 행동, 화면과 수치로 확인한다.
4. 답으로 바뀐 결정과 남은 질문만 짧게 보여준다. 새 모순과 범위 변화도 확인한다.
5. 목표, 범위, 중요한 제약과 성공 판정을 사용자에게 확정받으면 SDD로 간다. 미결은 답변 완료, 조사로 확인, 사용자 보류로 구분한다. 보류 이유와 재개 조건을 남기고, 혼자 보류하지 않는다.

## 확인할 관점

- 누가 언제 무엇을 하려다 막히는가. 이 기능이 필요한 이유와 현재 우회 방법은 무엇인가.
- 끝나면 무엇이 달라져야 하는가. 실제로 사용 가능한 결과까지 이번 범위인가.
- 기존 뼈대와 데이터, 인터페이스에서 유지할 것은 무엇인가. 변경을 허용하는 경계는 어디인가.
- 기한과 비용, 운영상의 제약은 무엇인가. 이번에는 하지 않을 일은 무엇인가.
- 무엇을 보고 성공이나 실패라고 판단할 것인가. 화면과 실제 동작, 데이터 확인이 필요한가.

필요한 관점만 묻되 초안과 승인 질문 한 번으로 깊은 인터뷰를 대신하지 않는다. 코드와 실행으로 확인할 사실은 직접 조사해 설명한다. 사용자에게 사실 추측을 요구하지 않으며 목표, 선호와 제품 정책은 사용자가 결정한다.

## 질문과 결과 표현

선택지의 실제 영향과 장단점을 짧게 설명하고 추천은 추천으로 표시한다. 용어만 던지거나 특정 해석을 질문에 몰래 확정해 넣어 유도하지 않는다. 정답 없는 열린 결정은 자유 답변을 받는다.

설계가 모호하면 목업이나 폐기용 실험으로 비교할 수 있다. 실험 결과로 사용자 선호를 대신 결정하지 않는다. 새 외부 작업과 데이터 생성 전에는 권한과 프로젝트 지침을 확인한다.

기본 보고는 “해결할 문제, 원하는 결과, 범위와 비목표, 남은 결정”이다. 명확히 답한 결정은 재사용하고, 미결을 추측으로 없애지 않는다.

문서 모드의 새 작업은 [의도 템플릿](../assets/intent-template.md)으로 `intent.md`에 초안을 저장한 뒤 확인받는다. `task.md`에는 의도의 상대 링크와 상태를 남긴다. 확정 후 사용자 답변, 확정 범위, 미결과 보류를 작업 기록의 결정 이력에 적고 단계를 갱신한 뒤 SDD로 간다. 기존 의도 정본은 해당 위치에서 이어 쓴다.

새 기능과 방향은 의도를 자세히, 작은 결함은 짧게 기록한다. 미결에 질문 ID를 붙여 SDD의 처리 위치로 연결한다. 성공 판정 자료와 순서, 기존 구조의 변경 허용 경계도 확인한다. 경로와 저장 시점은 [작업 상태 지침](../references/work-state.md)을 따른다.
