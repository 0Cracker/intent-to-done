# 의도 인터뷰

결과는 사용자의 문제와 원하는 결과가 명확하고, 무엇을 하지 않을지도 사용자가 판단할 수 있는 짧은 의도다.

1. 사용자 말과 기존 확정 사항으로 초안을 먼저 쓴다. 문제, 영향을 받는 사람과 상황, 원하는 결과, 범위, 제약, 비목표, 성공 판정의 근거를 표시한다.
2. 빈칸과 두 가지로 읽히는 표현을 찾아 한 번에 1~3개씩 질문한다. 관련 질문이 남으면 여러 차례 이어간다. 질문 수를 채우려고 이미 답한 것을 반복하지 않는다.
3. 구체적인 현재 사례, 원하지 않는 결과와 반대 사례를 요청한다. “좋게”, “빠르게”, “예쁘게”가 무엇을 뜻하는지 사용자의 행동과 화면, 수치의 의미로 확인한다.
4. 답이 바꾼 결정과 남은 질문만 짧게 보여준다. 답변이 새로 만든 모순과 범위 변화도 다시 확인한다.
5. 사용자가 목표, 범위, 중요한 제약과 성공 판정을 확정하면 SDD로 간다. 미결은 답변 완료, 조사로 확인, 사용자 보류로 구분한다. 보류에는 이유와 재개 조건을 남기고 혼자 보류 처리하지 않는다.

## 확인할 관점

- 누가 언제 무엇을 하려다 막히는가. 이 기능이 필요한 이유와 현재 우회 방법은 무엇인가.
- 끝나면 무엇이 달라져야 하는가. 실제로 사용 가능한 결과까지 이번 범위인가.
- 기존 뼈대와 데이터, 인터페이스에서 유지할 것은 무엇인가. 변경을 허용하는 경계는 어디인가.
- 기한과 비용, 운영상의 제약은 무엇인가. 이번에는 하지 않을 일은 무엇인가.
- 무엇을 보고 성공이나 실패라고 판단할 것인가. 화면과 실제 동작, 데이터 확인이 필요한가.

해당 작업에 필요한 관점만 묻되, 초안 한 번과 승인 질문만으로 깊은 인터뷰를 대신하지 않는다. 코드나 실행으로 확인할 수 있는 사실은 직접 조사해 설명하고 사용자에게 사실 추측을 요구하지 않는다. 목표와 선호, 제품 정책은 사용자가 결정한다.

## 질문과 결과 표현

선택지가 있으면 실제 영향과 장단점을 짧게 설명하고 추천안은 추천으로 표시한다. 사용자에게 용어만 던지지 않는다. 한 해석을 질문에 몰래 확정해 넣거나 유도하지 않는다. 정답이 없는 열린 결정은 자유 답변을 받는다.

설계가 모호하면 목업이나 폐기용 실험으로 비교를 도울 수 있다. 실험 결과만으로 사용자 선호를 대신 결정하지 않는다. 새 외부 작업이나 데이터 생성은 현재 권한과 프로젝트 지침을 먼저 확인한다.

기본 보고는 “해결할 문제, 원하는 결과, 범위와 비목표, 남은 결정”이다. 이미 명확히 답한 결정은 재사용하고, 미결을 에이전트 추측으로 없애지 않는다.
