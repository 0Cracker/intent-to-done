# SDD와 구현 계획 인터뷰

확정 의도를 관찰 가능한 계약과 구현 방향으로 구체화한다. 기존 프로젝트는 how로 실제 흐름을 확인하고, 구조 변경 시 필요한 why 근거를 읽는다. 새 프로젝트의 코드와 실행 결과를 지어내지 않는다.

## 충분히 인터뷰할 내용

한 번에 1~3개씩 묻고 답변의 영향과 남은 빈틈을 확인한다.

- 정상 흐름: 시작 조건, 입력, 처리, 화면이나 응답, 완료 후 상태.
- 관련 예외: 빈 상태, 잘못된 입력, 실패, 취소, 중복 조작, 화면 이동, 재시도와 동시 실행 중 실제로 관계있는 상황.
- 유지할 계약: 기존 동작과 데이터 의미, 공개 API, 호환성, 보존과 접근 조건.
- 성공 판정: 정상, 예외, 관련 회귀 시나리오와 기대 결과, 검사 수단.
- 구현 방향: 대안별 사용 경험과 유지보수, 비용과 위험, 가장 위험한 작업과 되돌리기.
- 작업 순서: 작동하는 기능 단위, 변경할 범위, 소유자와 의존 관계.

사양과 구현 방향은 추천하되 임의로 확정하지 않는다. 기술 선택의 영향도 쉬운 말로 설명한다. 사실 조사와 단순 실행을 선호 결정처럼 되묻지 않는다. 승인된 구현 방향 안의 지역적 코딩 선택은 구현 담당에게 맡길 수 있다. 계약과 위험을 바꾸는 선택은 다시 확인한다.

## 사양에 남길 최소 내용

- 의도와 관련 정본 링크.
- 현재 동작과 바꿀 동작, 제약과 비목표.
- 인수 조건별 시나리오와 기대 결과, 검사 방법.
- 핵심 결정과 근거, 미결과 사용자 보류.
- 구현 단위와 순서, 위험과 필요한 확인.

문서 모드의 새 작업은 [SDD 템플릿](../assets/spec-plan-template.md)으로 `SDD.md`에 계약과 검증 계획을, [구현 템플릿](../assets/implementation-template.md)으로 `implementation.md`에 작업 순서와 위험을 저장한다.

[작업 상태 지침](../references/work-state.md)에 따라 사양 버전과 인수 조건 ID를 붙이고, 승인 요청 전 두 문서를 저장한다. 답변 후 승인 버전, 단계 범위와 조건을 `task.md` 이력에 남긴다. 기존 정본은 구조를 유지하고 링크한다.

의도의 모든 질문을 SDD의 답변, 조사나 사용자 보류로 연결한다. 인수 조건에서 구현 작업 단위와 검증 방법까지 추적할 수 있게 한다. 다른 세션이나 구현 담당자에게 넘길 때만 [인계 템플릿](../assets/handoff-template.md)을 쓰고 기존 승인 범위를 명시한다. 인계와 장기 작업은 대화 없이도 목표, 계약, 범위와 검증을 이해할 계획을 남긴다.

테스트 기대값은 사양에서 정하며 미결을 코드에 맡기지 않는다. 변경 전후 흐름, 성공 조건과 선택지를 사용자에게 확정받는다. 구현을 막는 미결은 해결하거나 사용자 승인으로 범위를 좁힌다.

## 새 프로젝트와 테스트 환경

테스트 실행기나 최소 골격이 없으면 필요한 도구와 최소 준비 범위를 계획에 넣어 확인받는다. 준비는 테스트 실행에 필요한 설정과 골격까지이며 기능 로직의 사전 작성 승인이 아니다. 새 의존성, fixture, 스키마와 데이터 변경은 프로젝트 규칙을 따른다.

컴파일 언어나 새 인터페이스는 기능 로직 없는 선언과 stub이 필요할 수 있다. 준비 범위를 설명하고 이후 실패가 미구현 계약 때문인지 확인한다. 오탈자, 잘못된 경로와 미설치 도구의 실패는 TDD 근거가 아니다.
