# SDD와 구현 계획 인터뷰

확정 의도를 관찰 가능한 계약과 구현 방향으로 구체화한다. 기존 프로젝트에서는 how로 실제 흐름을 확인하고, 구조를 바꾸려면 필요한 why 근거를 읽는다. 신규 프로젝트에서는 존재하지 않는 코드와 실행 결과를 만들어내지 않는다.

## 충분히 인터뷰할 내용

한 번에 1~3개씩 질문하고 답변의 영향과 남은 빈틈을 후속 확인한다.

- 정상 흐름: 시작 조건, 입력, 처리, 화면이나 응답, 완료 후 상태.
- 관련 예외: 빈 상태, 잘못된 입력, 실패, 취소, 중복 조작, 화면 이동, 재시도와 동시 실행 중 실제로 관계있는 상황.
- 유지할 계약: 기존 동작과 데이터 의미, 공개 API, 호환성, 보존과 접근 조건.
- 성공 판정: 정상, 예외, 관련 회귀 시나리오와 기대 결과, 검사 수단.
- 구현 방향: 대안별 사용 경험과 유지보수, 비용과 위험, 가장 위험한 작업과 되돌리기.
- 작업 순서: 작동하는 기능 단위, 변경할 범위, 소유자와 의존 관계.

에이전트가 추천은 하되 사양과 구현 방향을 임의로 확정하지 않는다. 사용자가 판단할 수 있도록 어려운 기술 선택도 영향을 쉬운 말로 설명한다. 사실 조사와 단순 기계적 실행을 선호 결정인 것처럼 계속 되묻지 않는다. 승인한 구현 방향 안의 지역적인 코딩 선택은 구현 담당이 수행할 수 있다. 계약과 위험을 바꾸는 선택은 다시 확인한다.

## 사양에 남길 최소 내용

- 의도와 관련 정본 링크.
- 현재 동작과 바꿀 동작, 제약과 비목표.
- 인수 조건별 시나리오와 기대 결과, 검사 방법.
- 핵심 결정과 근거, 미결과 사용자 보류.
- 구현 단위와 순서, 위험과 필요한 확인.

기존 문서에 맞춰 통합하고 매 단계 새 파일을 만들지 않는다. 작은 작업은 짧은 항목으로 충분하다. 인계나 장기 작업에는 대화 없이도 목표와 계약, 범위와 검증을 이해할 수 있는 계획을 남긴다.

테스트 기대값은 사양에서 정한다. 미결을 코드가 정해줄 것이라며 넘기지 않는다. 사용자에게 변경 전후 흐름과 성공 조건, 선택지를 제시하고 확정받는다. 구현을 막는 미결은 해결하거나 사용자가 승인한 더 좁은 범위로 조정한다.

## 새 프로젝트와 테스트 환경

테스트 실행기나 최소 골격이 없으면 필요한 도구와 최소 준비 범위를 계획에 포함해 확인받는다. 허용된 준비는 테스트가 실행될 정도의 설정과 골격이며, 기능의 실제 처리 로직을 미리 작성하는 승인이 아니다. 새 의존성과 fixture, 스키마나 데이터 변경은 프로젝트 규칙을 따른다.

컴파일 언어나 새 인터페이스는 기능 로직 없는 선언과 stub이 필요할 수 있다. 준비 범위를 설명하고, 이후 실패가 실제 미구현 계약을 드러내는지 확인한다. 단순 오탈자나 잘못된 경로, 미설치 도구 때문에 발생한 실패를 TDD 근거로 쓰지 않는다.
