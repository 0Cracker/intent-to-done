# 테스트 설계와 TDD

## 사양에서 검사로

확정 인수 조건마다 관련 시나리오, 입력과 사전 조건, 기대 결과, 검사 수단을 연결한다. 정상, 관련 예외와 유지할 기존 동작을 포함한다. 기대 동작이 미정이면 SDD 인터뷰로 돌아간다.

가장 가까운 기존 단위, 컴포넌트, 통합, 회귀 검사 중 실제 계약을 확인할 수 있는 것을 고른다. UI는 필요에 따라 조작 검사를, API는 요청과 응답 검사를 포함한다. 단위 검사만으로 실제 경계 연결까지 확인했다고 하지 않는다.

## 시작 근거와 사용자 확인

- 신규 동작과 버그: 기능 코드 변경 전에 테스트를 작성하고 실제 실행해 예상한 이유의 RED를 확인한다. 환경 불가와 무관한 실패는 RED가 아니다. 이미 기능이 존재하면 그 사실을 조사하고 불필요한 변경을 하지 않는다.
- 동작 보존 리팩터링: 변경 전 동작을 고정한 검사나 동등성 비교를 실행해 통과 기준선을 확보한다. 기능을 일부러 깨뜨려 RED를 만들지 않는다.
- 자동 예외: 동작 변경 없는 문서, 주석, 포맷팅과 폐기용 목업, 프로토타입에 한정한다. 이유와 대체 검증을 보고하며 제품 편입은 정상 절차를 따른다.
- 그 밖에 테스트가 어렵거나 비싼 경우: 장애와 대체 방안을 사용자에게 보고한다. 자동 예외에 몰래 추가하지 않는다.

처음에는 쉬운 시나리오와 실제 실행 결과를 함께 제시하고 구현 진행을 확인받는다. 자동 진행을 허용한 구간이면 이 대기는 생략한다.

이후 승인한 구현 단위에서는 확정 사양 안의 추가 테스트를 자동 작성하고 실행한다. 추가 테스트도 새 동작이나 버그 검증이면 기능 변경 전 예상한 실패를 확인한다. 다음 별도 기능 단위의 최초 확인을 생략하거나, 사양에 없던 기대 동작을 정하는 권한으로 해석하지 않는다.

## 좋은 테스트의 규칙

1. 기대값은 요구와 독립된 근거에서 구한다. 검사 대상 함수의 반환값으로 정답을 계산하거나 테스트가 만든 데이터만 검사하지 않는다.
2. 반환값, 오류, 읽을 수 있는 상태, 화면과 외부 효과 등 관찰 가능한 계약을 확인한다. 내부 helper 호출과 호출 순서만 고정하지 않는다. 외부 요청의 횟수나 payload가 계약이면 확인할 수 있다.
3. 동작을 깨뜨리면 실패하고, 결과를 유지한 내부 구조 변경에는 계속 통과하는 검사인지 검토한다.
4. 시간, 임의 값, 공유 상태와 실행 순서에 불필요하게 의존하지 않는다. 간헐 실패는 조건을 좁히거나 계측하고 제한을 남긴다.
5. mock만 맞는 검사와 과도한 fixture 변경을 피한다. 관련 외부 경계를 검증하는 통합 검사는 사용한다.
6. 검사를 삭제하거나 skip하고 잘못된 구현에 맞춰 기대값을 바꾸어 통과시키지 않는다. 테스트 자체가 틀렸다면 확정 계약에 근거한 수정 이유를 기록한다. 기대 동작 변경은 사용자 확인이 먼저다.

## 반복과 근거

작은 기능 단위로 RED → 최소 구현 → GREEN → 필요한 리팩터링 → 재검증을 반복한다. 사양 전체의 모든 테스트를 구현 전에 완성하도록 강제하지 않는다. 리팩터링만 수행하면 기준선 → 구조 변경 → 동등성 확인을 반복한다.

실행 명령과 작업 위치, 코드 상태와 관련 환경, 실제 결과를 남긴다. 사용자 보고에는 “어떤 상황을 확인했는가, 기대한 것, 실제 결과와 이유”를 먼저 보여주고 전체 로그를 연결한다. 실행하지 않은 출력 예시를 실제 결과처럼 쓰지 않는다.

보호 목적은 기준의 약화를 막는 것이다. 테스트 파일 편집 자체나 RED 상태의 커밋을 일괄 강제하지 않는다. 프로젝트의 커밋과 검사 규칙을 따른다.
