# 독립 검증과 마감

변경 작업은 자체 검증과 별도로, 새 컨텍스트의 검증 담당자 한 명에게 확인시킨다. 현재 스킬은 이 범위의 위임을 요청한다. 필요할 때 추가 검토자를 사용하더라도 주 담당 포함 동시 총 3개 상한을 지킨다.

## 검증자에게 전달할 것

- 원래 요청과 확정 사양, 인수 조건, 제약과 비목표.
- 저장소와 대상 파일, 비교할 기준과 대상 코드 상태, 재현 가능한 실행 방법.
- 알려진 기존 실패와 환경 제한, 이전부터 이어진 같은 문제의 수정 횟수.

구현자의 “잘 됐다”는 결론을 정답으로 주지 않는다. 테스트와 실제 코드는 읽게 하며 전체 대화와 불필요한 파일을 복제하지 않는다. 검증자는 제품 코드를 수정하거나 허가 없이 하위 검증자를 늘리지 않는다. 격리된 재현 스크립트나 검사는 권한 내에서 실행할 수 있다.

도구가 새 컨텍스트의 검증자를 실행하지 못하면 같은 세션의 재검토를 독립 검증이라고 부르지 않는다. 사용자에게 다른 세션으로 넘길 짧은 검증 요청을 준비하고, 실행되기 전까지 검증 완료를 보류한다.

## 확인할 내용

1. 사양의 각 조건이 실제 구현과 테스트에 반영됐는지 대조한다.
2. 중요한 입력, 실패와 인접 경로, 기존 계약의 회귀를 관련 범위에서 확인한다.
3. 기대값과 검사가 구현을 그대로 따라 쓴 것은 아닌지, 실제 동작을 검사하는지 검토한다.
4. 변경 대상의 실제 경계에서 확인한다. UI는 실제 조작, API는 요청과 응답 등 적합한 방법을 사용한다. 다른 대상을 검사한 결과로 대체하지 않는다.
5. 근거가 있는 결함은 재현 명령, 실제와 기대 결과, 영향과 코드 위치를 보고한다. 실행 불가나 미재현 위험은 확인된 결함과 구분하되 숨기지 않는다.

정적 근거로 명백한 문제를 발견했다면 해당 경로와 근거를 제시하고, 실행 재현 여부는 별도로 표시한다. 실행만을 이유로 의미 있는 미확인 위험을 삭제하지 않는다.

## 결과와 수정

결과는 “조건 충족”, “문제 발견”, “검증 불가”로 구분하고 범위와 실행 근거를 적는다. “조건 충족”은 검사한 범위에 한정되며 결함이 없다는 보장은 아니다. 단위 검사와 빌드 통과만으로 사용자 경험 전체의 성공을 선언하지 않는다.

문제는 주 담당이 확정 사양 안에서 수정한다. 구현 중 자체 검증부터 이어진 같은 문제의 수정 횟수는 합산한다. 변경 후 영향받는 조건을 다시 검증하고, 코드가 달라졌으면 이전 판정을 그대로 최신 판정으로 쓰지 않는다.

필수 검증을 못 했거나 두 차례 수정 뒤에도 실패가 남으면 구현 상태와 근거, 보류 이유와 필요한 다음 조치를 보고한다. 검증 완료로 표시하지 않는다. 무관한 기존 실패는 명시하고 프로젝트의 필수 통과 조건을 따른다.

기본 모드에서는 독립 검증 보고를 사용자가 판단한 뒤 완료 보고로 넘어간다. 자동 진행 범위면 결과에 따라 마감한다.

## 마감

변경된 계약과 상태를 기존 정본에 갱신한다. 요약은 달라진 점, 실제 검증, 미확인과 남은 일이다. 구현, 검증, 배포 상태를 구분한다. 사양을 벗어난 변화와 해결하지 않은 결함을 감추지 않는다. 사용자에게 맡겨지지 않은 병합과 배포, 외부 전송으로 범위를 넓히지 않는다.
