# 작업 상태와 재개

## 기록 모드와 저장 위치

의도, 사양, 테스트, 구현, 독립 검증 중 여러 단계를 거치는 변경은 크기와 무관하게 문서 모드를 쓴다. 한 응답으로 끝나고 인계가 없는 조사와 설명, 단일 단계의 문서, 주석, 포맷 수정은 대화 모드를 쓸 수 있다. 기록을 요청받으면 문서 모드를 쓴다.

대화 모드에서 사용자 판단 대기, 세션 인계, 위임이나 여러 단계의 변경으로 확대되면 첫 대기나 인계 전 문서 모드로 전환한다. 기존 요청, 결정과 근거를 옮기고 확인 불가한 과거 승인은 미확인으로 남긴다. 문서 모드로 시작하면 완료까지 같은 정본을 유지한다.

1. 프로젝트 지침과 기존 문서 경로, 구조를 우선한다. 사양과 계획이 다른 문서에 있으면 정본으로 유지하고 작업 기록에서 링크한다. 중복 관리하지 않는다. 기존 통합 문서도 재개 시 유지하며, 분리를 요청받았을 때만 원래 위치의 링크와 이력을 보존해 나눈다.
2. 기존 문서 구조가 없으면 아래 기본 구조를 쓴다. 사용자에게 경로를 정하게 하지 말고 작업 ID에 맞춰 필요한 폴더와 파일을 만든 뒤 위치를 보고한다. Git이 없으면 사용자가 지정한 작업 디렉터리를 루트로 쓴다. 경계가 불명확하면 확인하며 홈이나 스킬 설치 폴더를 프로젝트 루트로 간주하지 않는다.
3. 작업 ID는 목표를 나타내는 짧은 이름으로 정한다. 재개 시 기존 ID와 경로를 재사용한다. 다른 작업과 이름이 겹치면 접미사를 붙이고 기존 파일을 덮어쓰지 않는다.
4. 새 문서는 아래 템플릿을 실제 내용으로 채운다. 기존 문서는 빠진 항목만 보완하고 제목과 구조를 일괄 교체하지 않는다. 정본 경로를 최초 보고와 인계에 포함한다.

```text
docs/
└── tasks/
    └── <작업-id>/
        ├── task.md            # 현재 상태, 문서 위치, 승인과 변경 이력
        ├── intent.md          # 문제, 목표, 범위와 미결
        ├── SDD.md             # 동작 계약, 인수 조건과 검증 계획
        ├── implementation.md  # 구현 순서, 변경 내역과 실제 실행 근거
        ├── report.md          # 독립 검증, 최종 결과와 남은 일
        ├── handoff.md         # 다른 세션으로 실행을 넘길 때만
        └── evidence/          # 실제 로그와 캡처가 생길 때만
```

위 트리는 완성된 배치 예이며 시작 시 전부 만들지 않는다. 의도 단계는 `task.md`와 `intent.md`, 사양과 계획은 `SDD.md`와 `implementation.md`, 독립 검증이나 부분 마감은 `report.md`를 만든다. 해당 단계 전에는 미진행으로만 표시한다.

새 사양 파일명은 대소문자를 포함해 `SDD.md`로 쓴다. 기존 `sdd.md`, `spec.md`나 통합 문서가 정본이면 중복 생성하거나 이름을 바꾸지 않는다. 의도나 사양에서 마감하면 보고서에 해당 단계의 부분 결과만 담고 미실행 구현과 검증 문서는 만들지 않는다.

문서끼리는 실제 상대 링크로 연결한다. `task.md`에 문서별 위치와 상태를 두고, 없는 파일은 링크 대신 미작성으로 표시한다. 새 작업은 별도 폴더에 모으고 무관한 기존 `docs/` 문서는 옮기지 않는다.

템플릿의 빈칸과 기본 상태는 사실이나 승인이 아니다. 진행 전 단계는 미진행으로 둔다. 권한이나 사용자 제약으로 저장할 수 없으면 미저장 이유와 인계용 요약을 제공한다. 파일 저장과 재개 준비를 완료로 보고하지 않는다.

## 문서의 깊이와 상세 템플릿

기록 모드와 문서 길이는 별개다. 작은 결함도 새 문서 모드라면 위 파일 구성을 따르되 몇 줄로 작성할 수 있다. 무관한 표를 채우려고 결정을 만들지 않는다. 새 기능과 방향은 의도를, 여러 경계의 변경은 사양과 계획을 자세히 기록한다. 대화 모드의 단순 설명에는 작업 폴더를 만들지 않는다.

| 필요 | 사용할 템플릿 | 기본 저장 방식 |
| --- | --- | --- |
| 작업 시작과 재개 | [작업 기록](../assets/task-template.md) | `task.md`에 현재 상태, 문서 목록과 승인 이력 유지 |
| 의도와 범위의 구체화 | [의도](../assets/intent-template.md) | `intent.md`에 문제, 목표, 판정 방식과 미결 기록 |
| 계약과 검증 계획의 구체화 | [SDD](../assets/spec-plan-template.md) | `SDD.md`에 사양 버전, 인수 조건과 설계 결정 기록 |
| 구현 준비, 테스트와 변경 | [구현 계획과 기록](../assets/implementation-template.md) | `implementation.md`에 작업 순서, 실행별 근거와 변경 결과 누적 |
| 독립 검증, 중단 또는 최종 보고 | [결과보고서](../assets/report-template.md) | `report.md`에 검사한 대상, 판정과 구현, 검증, 배포 상태 기록 |
| 다른 세션이나 구현 담당자에게 실행을 넘김 | [인계 지시](../assets/handoff-template.md) | 인계가 필요할 때만 작업 문서 옆 `handoff.md` 작성, 작은 위임은 같은 내용을 담은 짧은 요청으로 충분 |

템플릿은 해당 단계에서 필요한 섹션만 읽어 쓴다. 의도 질문은 `intent.md`, 확정 계약은 `SDD.md`, 작업 순서와 실행 이력은 `implementation.md`, 검증 판정과 최종 결과는 `report.md`가 맡는다. 승인과 변경 이력, 문제별 누적 수정 횟수는 `task.md`에서만 관리하고 다른 문서는 링크한다. 기존 프로젝트는 같은 역할의 문서에 대응시킨다.

인계에는 대화 없이도 목표, 계약, 작업 순서, 소유 경계, 검증과 남은 권한을 판단할 요약을 담는다. 기준 사양 버전과 코드 상태를 표시하고 정본 변경 시 유효성을 재확인한다. 인계 파일 작성은 구현 권한을 부여하지 않는다.

## 의도에서 마감까지 연결할 내용

- 미결에 `Q-001` 같은 ID를 붙여 답변, 조사 필요, 미결과 사용자 보류를 구분한다. 사양에서 질문별 답과 반영 위치, 남은 조사나 사용자 보류 조건을 연결한다. 담당자와 기한이 없으면 미정으로 두고, 질문을 조용히 삭제하거나 혼자 보류하지 않는다.
- 원하는 결과는 사양의 인수 조건으로, 판정 자료와 확인 순서는 검증 계획으로 연결한다. 기존 구조의 변경 허용 경계와 비목표도 반영한다. 숫자와 코드 위치는 실제 조사에 근거하며 의도 단계의 미확인 값을 억지로 채우지 않는다.
- 중요한 설계는 선택 이유와 확인한 대안을 남긴다. 관측 사실, 사용자 확정과 에이전트 제안을 구분한다. 미결 제품 정책을 코드나 템플릿 기본값으로 확정하지 않는다.
- 여러 작업 단위는 `T-001` 같은 ID로 인수 조건, 파일과 소유자, 선행 계약, 완료 검사를 연결한다. 필요한 범위에서 가장 위험한 단계와 되돌릴 방법을 남긴다. 작은 단위 하나에 별도 작업 대장을 만들지 않는다.
- 요구에서 구한 기대 결과와 실제 관찰을 나눠 적는다. 실행으로 확인한 결함, 정적 근거와 미확인 위험을 구분한다. 미실행을 삭제하거나 통과로 바꾸지 않는다. 마감에는 지금 쓸 수 있는 범위와 추가 환경, 릴리스 필요 여부를 포함한다.

## 현재 상태와 단계별 기록

`task.md` 상단에 현재 상태를, 문서 목록에서 연결한 정본에 단계별 상세를 남긴다. 상태와 요약을 갱신할 때 원본 판정과 대조한다.

| 항목 | 남길 내용 |
| --- | --- |
| 현재 상태 | 단계, 진행 중 또는 사용자 판단 대기, 중단 이유 |
| 기록 위치 | 프로젝트 루트, 기록 모드와 작업 문서 경로 |
| 요청과 정본 | 원래 요청 요약, 사양과 계획의 위치와 변경 식별 |
| 사양 버전 | 현재 버전, 초안 또는 확정, 인수 조건별 변경과 승인 근거 |
| 결정 | 확정, 추천, 미결과 사용자 보류를 구분한 현재 결정 |
| 진행 권한 | 수동 또는 자동 구간, 별도로 위임한 결정권의 범위 |
| 코드 상태 | 저장소, branch와 HEAD, 관련 미커밋 변경과 사용자 변경 |
| 검증 | 인수 조건별 검사와 실제 결과, 대상 코드 상태와 환경, 기존 실패와 미확인 |
| 수정 횟수 | 근본 문제별 수정과 재검증 횟수, 각 시도 근거 |
| 다음 행동 | 남은 질문, 필요한 환경과 승인, 다음 실행 지점 |

| 단계 | 저장 위치와 남길 내용 | 저장 시점 |
| --- | --- | --- |
| 0. 현황 | `task.md`에 원래 요청, 작업 경계, 실행 환경, 기존 실패와 문서 위치 | 최초 조사 후, 첫 사용자 판단 대기 전 |
| 1. 의도 | `intent.md`에 문제, 목표, 범위, 비목표, 제약, 성공 판정과 미결 | 초안 제시 전과 사용자 확정 직후 |
| 2. 사양과 계획 | `SDD.md`에 계약과 인수 조건, `implementation.md`에 구현 순서와 위험 | 승인 요청 전과 확정 직후, 사양 변경 시 |
| 3. 테스트 | `implementation.md`에 테스트 위치, 실제 RED 또는 기준선과 실행 근거, `task.md`에 진행 권한 | 최초 실행 후, 구현 승인 요청 전 |
| 4. 구현 | `implementation.md`에 변경과 자체 검증, 사양과의 차이, `task.md`에 누적 수정 횟수 | 기능 단위 완료와 수정 재검증 후, 독립 검증 인계 전 |
| 5. 독립 검증 | `report.md`에 검증 담당, 대상 코드 상태와 조건별 판정, 실행 근거는 `implementation.md`에 연결 | 결과 수신 후, 사용자 판단 대기와 다음 수정 전 |
| 6. 마감 | `report.md`에 구현, 검증, 배포 각각의 상태와 남은 일, `task.md`에 최종 상태와 다음 행동 | 최종 보고 전 |

사용자 판단 대기와 단계 전환 시 현재 상태와 다음 행동을 갱신한다. 승인 대기 중에는 초안과 미승인을 유지하고 답변 후 승인 결과를 저장한다. 중단과 인계 전 자동 진행 범위, 미결, 검증 제한과 수정 횟수도 저장한다. 매 대화 턴과 파일 편집마다 기록을 늘리지는 않는다.

## 승인, 변경과 수정 이력

- 사양은 `r1`부터 시작하며 기대 동작, 인수 조건, 범위나 중요한 제약 변경 시 버전을 올린다. 문구와 서식 변경만으로 올릴 필요는 없다. 기존 버전 규칙이 있으면 따른다.
- 결정 이력에 대상 섹션, 사양 버전, 결정 내용, 사용자 답변의 짧은 인용이나 확인 가능한 메시지 식별자, 승인 단계와 범위, 보류와 조건을 남긴다. 자동 진행과 결정권 위임의 범위도 기록한다. 확인 불가한 시각과 메시지 ID는 만들지 않는다.
- 결정을 대체하면 변경 전후, 이유와 대체 관계를 이력에 추가한다. 현재 사양을 갱신하되 승인 당시 계약과 근거를 복원할 수 있게 남긴다. 새 버전 전체를 자동 승인으로 보지 않고 유지되는 승인과 재확인할 변경을 구분한다.
- 문서 모드의 인수 조건에 `AC-001` 같은 안정적인 ID를 붙여 테스트 파일과 케이스, 실행 결과와 독립 판정을 연결한다. 삭제하거나 대체한 조건의 ID를 다른 의미로 재사용하지 않는다. 별도 추적 대장은 만들지 않는다.
- 근본 문제별로 고정 ID를 붙인다. 상한에 포함되는 수정과 재검증 후 시도 번호, 변경 이유와 근거, 결과를 이력에 추가하고 누적 횟수를 갱신한다. 재개, 담당과 사양 변경만으로 두 차례 상한을 초기화하지 않는다. 추가 수정 지시를 받으면 기존 횟수와 새 허용 범위를 함께 남긴다.

## 실행 근거 보관

실행마다 사양 버전, 인수 조건 ID, RED, GREEN, 기준선 또는 독립 검증 구분, 실행 시각, 명령, 작업 위치, 대상 코드 상태, 관련 환경, 실제 결과와 종료 코드를 남긴다. 수동 검사는 실제 조작과 관찰을 적고 종료 코드를 지어내지 않는다. 미실행은 이유와 다음 조치를 남긴다.

대상 코드 상태는 Git의 branch, HEAD와 관련 미커밋 변경을 포함한다. 같은 HEAD에서도 코드가 다를 수 있으므로 대상 코드와 테스트의 미커밋, 미추적 파일을 목록과 해시 또는 보존된 diff 등으로 식별한다. Git이 없으면 명시하고 대상 파일과 해시 등을 쓴다. 기록을 위해 자동 커밋하거나 사용자 변경을 초기화하지 않는다.

짧은 실행 결과는 `implementation.md`에 직접 남기고, `report.md`는 해당 실행을 링크해 판정한다. 긴 로그와 캡처는 기존 보관 경로에, 없으면 같은 작업 폴더의 `evidence/`에 저장해 상대 링크로 연결한다.

`<순번>-<검사구분>.log` 같은 고유 이름으로 실행별 근거를 보존하며 RED 로그를 GREEN으로 덮어쓰지 않는다. 실제 파일이 생길 때만 폴더를 만든다. 인증 정보와 민감 데이터는 제외하거나 가리고 검증 제한도 표시한다.

## 재개

재개 시 프로젝트 지침과 기존 작업 문서를 찾는다. 기본 구조에서는 `task.md`의 현재 상태, 정본 목록, 승인 이력과 수정 횟수를 먼저 읽는다. 필요한 `intent.md`, `SDD.md`, `implementation.md`, `report.md`로 이어간다.

실제 코드와 최신 사용자 지시를 대조하고 같은 목표의 폴더를 중복 생성하지 않는다. 승인과 보류를 보존하고 달라진 범위만 재확인한다. 문서의 완료 표시로 현재 코드의 완료나 검증 통과를 단정하지 않는다. 코드 변경 시 이전 결과는 당시 근거로 보존하고 영향받는 현재 판정만 재검증 필요로 바꾼다. 유효한 다른 결정은 초기화하지 않는다.

순수 사양 변경 시 영향받는 테스트와 구현 계획도 갱신한다. 같은 근본 문제의 자동 수정 횟수는 이어간다. 추가 수정 지시의 새 범위를 기록한다. 요약에서도 미결, 미확인과 자동 진행 권한의 경계를 보존한다.
